## 3. 测试方法与适配

标准播放器无法打开该文件，本次使用临时 Python 测试脚本，以 `rb` 打开同一个原文件，逐块解析到内存，并按原记录时间间隔以 1 倍速发布选定话题。文件没有被修复，内存中的读取信息也不写回磁盘。测试脚本只是数据发送工具；健康判定仍由现有 **C++ V2 节点**执行。

使用独立 ROS master `http://127.0.0.1:33519`，不干扰原先运行在 11311 的工程。不启动 FAST-LIO；定位和配准点云取自包内已有结果，因此本次不是重新建图或定位精度真值评测。

| IMU 检测 | `/mavros/imu/data_raw` | `sensor_msgs/Imu` | 56,488 | 约 0 秒 |

测试工具：test_original_readonly.py（本机测试归档，未纳入仓库）。该脚本依赖本机 Noetic 的 bag 读取内部接口，是本次受损文件的诊断工具，不替代正式回放入口，不支持正式入口的空格暂停逻辑。

本次没有注入错误、补齐尾块、替换零时间戳、重排消息或生成新 bag。日志中的雷达异常来自输入本身；接收超时同时受原记录时序、Python 发送调度、ROS 传输及 C++ 回调调度影响，不能直接当成实机传感器失联结论。

时间指标的范围：检查源时间戳是否有效、是否递增、相邻间隔和源频率，并用单调时钟检查接收年龄。模板的 `stamp_domain` 标签仍为 `device_relative`，本次未做绝对时钟同步或端到端传输延迟验证；包内多数消息头数值呈 Unix 时间形式，不能把该标签解释成已经验证了时钟域。

## 4. 实测结果

已按原时序 1 倍速读取并发布完整可读区域，共 **286.3666 秒**。原生播放器仍不能直接打开原文件；这是专用只读脚本的诊断结果，不是原生回放成功。

| 输入 | 脚本发送 | 检测器最后代际计数 | 结果 |
| --- | ---: | ---: | --- |
| 雷达 | 2,421 | 2,421 | 一致 |
| IMU | 56,488 | 56,442 | 差 46 条，不能证明全量无丢失 |
| 定位 | 2,223 | 2,223 | 一致 |
| 已配准点云 | 2,223 | 不经过检测器 | 用于 RViz 显示 |

IMU 的计数属于当前数据代际：源码 `ModuleMonitor::control()` 在首次接入控制器时调用 `stream_.reset()`。本次 `INSTANCE_RESET` 晚于第一批 IMU 发送，存在启动计数清零因素；现有证据不能把这 46 条直接定性为原包缺消息或 ROS 传输丢包。**10 项工具核对为 9 项通过、1 项未通过；不宣称本轮全量无损接收验证通过。**

主要检测结果：

- 雷达仅首帧 `header.stamp=0`，触发 `STAMP_INVALID / ERROR`；后续有效时间戳恢复。有效源频率约 10.000 Hz，未发现时间戳回退或重复。
- IMU 有效源频率均值约 197.260 Hz，未发现非正时间戳、回退或重复。3 次 `STAMP_GAP / WARNING` 对应约 21.04、23.44、22.40 ms，超过当前 20 ms 阈值。
- IMU 两次运行段 `RECEIVE_AGE / WARNING` 约 102.10、106.16 ms，与脚本同步截图时机相邻。原记录最大 IMU 间隔仅约 75.38 ms，因此不能把这些接收告警直接解释为原始实机断流。
- 定位源频率约 9.999 Hz，未发现时间戳回退或重复；曾触发一次 `LOC_ACCELERATION / WARNING`，约 12.543 m/s²，阈值为 10 m/s²。
- 运行中三项曾同时 `OK / RUNNING`。80 秒以后、RUNNING 状态的每秒 CSV 采样中，雷达有效点比例为 1.0，采样点数 18,579～56,857；这不是所有帧的全量极值。
- 开头雷达/定位还未开始发布，超过模板 10 秒启动期限后出现启动超时；不能归类为运行中断流。末尾 `FAULT` 由脚本明确发布来标记受损文件的可读区域终止，不是定位算法崩溃，也不是正常 `STOPPED`。
- 保存的诊断中日志模块保持 OK；可读区域外的未完成尾块没有得到验证。

### 测试工具自身的核对

首次长回放结束时发现，Noetic 的延迟读取逻辑重复追加了已经在内存解析的消息位置，造成额外一次重复发送；该轮不作为包数据质量的结论。旧结果保留在 `discarded_duplicate_index_attempt/`，与正式结果分开。测试工具已设置 `_connection_indexes_read = True`，并在正式结果中逐项比对「原文件可读数量 → 脚本发送数量 → C++ 检测器接收数量」，避免将测试工具造成的回退、丢包或失联归因于原包。
