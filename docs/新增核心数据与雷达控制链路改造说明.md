# 新增核心数据与雷达控制链路改造说明

本文对应桌面交付版 `robot_health_monitor_v2_2026-10-19`，说明两类扩展：

1. 给健康检测增加一种新的核心数据和判断规则；
2. 让运行控制器订阅一个控制话题，并按话题内容启动或停止雷达驱动进程。

**当前代码状态：** `RuntimeController` 已有 `/robot_runtime/control` 服务，可控制运行配置中已有的进程组；当前运行配置示例只有 `localization` 组。通用 `std_msgs/Bool` 启停话题和 `lidar` 驱动组还没有加入代码。本文件中的控制话题代码是待实施的改造骨架，不代表现有版本已经支持。

## 1. 两条数据流先分清

```mermaid
flowchart LR
    A[外部控制节点] -->|std_msgs/Bool true/false| B[/robot_runtime/lidar_enable]
    B --> C[RuntimeController]
    C -->|RUN/STOP 受管进程| D[雷达 ROS 驱动]
    D -->|PointCloud2 等数据| E[健康监控适配器]
    E --> F[Sample]
    F --> G[流检查与雷达质量检查]
    G --> H[DiagnosticArray、RViz、日志]
    C -->|RuntimeState binding=lidar| E
```

控制话题表达外部要求的**期望状态**：`true` 要求驱动运行，`false` 要求驱动停止。健康诊断表达收到的数据是否正常。两者不能混成一个 `Bool`：雷达数据报错时，不一定应该停驱动；断流也可能正是驱动需要恢复的原因。

## 2. 新增核心数据：从消息到诊断的所有位置

### 2.1 先判断是不是确实需要扩展 `Sample`

项目的核心数据通道是 `Sample`，定义在 `include/fastlio_health_monitor/health_core.h`。已有数据可用就直接复用，不要为了一个新指标重复增加字段。例如：

- 已有 `orientation`：新增 pitch/roll 阈值时，通常在 `AttitudeTracker` 中从四元数计算角度即可，不必增加 `Sample.pitch`、`Sample.roll`。
- 已有 `range_m`：新增测距上下限时，只需扩展 `RangeChecker` 和 YAML 规则，不必增加新的距离字段。
- 只有消息里确实包含一种核心尚未表达的物理量（例如电池电压），且检查器要用数值计算时，才给 `Sample` 增加有单位的类型化字段。

`Sample` 保存供 C++ 规则计算的类型化数据；`Values` 保存便于诊断、RViz、CSV 展示的字符串。**如果只是一个可展示值，可以只写入 `Values`；如果需要可靠计算或跨模块复用，应增加类型化字段。**

### 2.2 需要改的文件与条件

| 位置 | 何时需要改 | 要做的事 |
| --- | --- | --- |
| `include/fastlio_health_monitor/health_core.h` | 核心确实需要一个新物理量，或需要一种新Checker | 给 `Sample` 加字段/可用性标记；新规则类声明并继承 `IHealthChecker`；必要时扩展 `ModuleConfig`。 |
| `src/input_adapters.cpp` | 输入消息格式还没有适配器，或现有适配器尚未把该字段写入 `Sample` | 在订阅回调中取时间戳、校验消息字段、做单位换算、填 `Sample`，再调用 `sink_(s)`；在 `AdapterFactory::create()` 注册适配器。 |
| `include/fastlio_health_monitor/input_adapters.h` | 需要改变公共适配器接口时 | 更新 `IInputAdapter` / `AdapterFactory` 声明。普通新增适配器类目前放在 `input_adapters.cpp` 的匿名命名空间里，**不一定要改这个头文件**。 |
| `src/health_core.cpp` | 新增Checker或新增可配置的质量阈值 | 增加 `qualityValidate()` 分支和阈值/单位校验；实现Checker；在 `CheckerFactory::create()` 注册名称。 |
| `config/health_robot.yaml`、`config/health_bag.yaml` | 新功能要用于实机或bag | 增加模块或该模块的 `quality` 规则；检测规则显式写 `enabled: true/false`；Topic、适配器、单位按消息实际情况填写。 |
| `test/health_core_test.cpp`、`test/optional_rules_test.cpp` | 每个新增判断规则 | 覆盖正常、WARNING、ERROR、关闭规则、边界值、无效值和单位换算；若新增测试源文件，再把它加入 `CMakeLists.txt` 的测试目标。 |
| `CMakeLists.txt` | 新增 `.cpp` 源文件、ROS消息依赖或自定义消息生成 | 把新源文件加入对应目标；若依赖新的消息包，在 `find_package(catkin ... COMPONENTS ...)` 和 `catkin_package()` 中加入依赖。 |
| `package.xml` | 新增外部ROS消息包依赖 | 增加对应 `<depend>包名</depend>`。标准 `std_msgs/Bool` 当前已经是依赖，无需为本控制话题新增依赖。 |
| `src/robot_health_monitor_node.cpp`、`src/health_panel.cpp`、`src/event_recorder.cpp` | 一般不用改 | 现有汇总层会把模块 `Values` 放进 `DiagnosticArray` 和周期指标CSV，RViz面板也按诊断键值显示。只有需要特殊布局或特殊事件格式时才改这些输出层。 |

`RuntimeState.msg` 和 `ControlModule.srv` 是进程生命周期接口，不是传感器数据接口。新增普通的质量数据不需要改它们。

`quality` 下面增加阈值时，通常不需要扩展 `ModuleConfig`；Checker读取已有的 `YAML::Node quality` 即可。若增加模块级字段（例如新的输入参数），则要同时扩展 `ModuleConfig`、`ConfigLoader::load()` 中的模块键白名单和字段解析，并把规范化值写进有效配置快照。

新增核心 `.cpp` 文件时，把它加入 `robot_health_core` 目标；新增ROS适配器源文件时，把它加入 `robot_health_monitor_node` 目标。若继续扩展现有 `health_core.cpp` / `input_adapters.cpp`，不用增加源文件列表。

### 2.3 示例：新增电压数据（伪代码）

以下用 `voltage_v` 举例说明一项真正的新数据需要经过哪些层。消息类型和阈值仅是示意，需替换成机器人真实接口和工程阈值。

#### A. 在 `Sample` 增加类型化数据

```cpp
// health_core.h 的 Sample 中
double voltage_v = 0.0;           // 电压，统一为 V
bool voltage_available = false;   // false表示消息没有可用电压，不能把默认0当测量值
```

若新增字段只在某一个Checker内部使用，也可以把它存于该Checker的私有状态；不要无理由把所有中间计算量塞进全局 `Sample`。

#### B. 在适配器中解包、校验和统一单位

```cpp
// input_adapters.cpp 中某个具体ROS消息回调的伪代码
void EnvironmentAdapter::callback(const robot_msgs::Environment::ConstPtr& msg) {
  Sample s;
  s.stamp = msg->header.stamp.toSec();
  s.received = steadyNow();
  s.frame = msg->header.frame_id;

  const double volts = msg->battery_voltage_mv * 0.001;  // mV -> V，只转换一次
  s.voltage_available = std::isfinite(volts);
  if (s.voltage_available) s.voltage_v = volts;
  s.values["voltage_v"] = s.voltage_available ? number(s.voltage_v) : "unavailable";

  // 消息结构正常；测量值是否可用由Checker生成明确Finding。
  sink_(s);
}
```

如果当前没有适配该ROS消息的类，需要在 `input_adapters.cpp` 增加实现，并在 `AdapterFactory::create()` 增加名称分支。新消息的ROS头文件只放在适配层，不要放进 `health_core.h`，这样健康核心不会依赖具体驱动包。

```cpp
// AdapterFactory::create()中的注册分支示意
if (c.adapter == "EnvironmentAdapter")
  return std::unique_ptr<IInputAdapter>(
      new EnvironmentAdapter(n, c, std::move(sink)));
```

普通订阅类通常继承当前文件里的 `AdapterBase`，在 `reconnect()` 中创建ROS订阅，在回调中组装 `Sample` 后调用 `sink_(s)`。如果新消息来自另一个ROS包，要把消息包加入 `CMakeLists.txt` 的catkin组件列表和 `package.xml`；若由本项目自定义，还要配置消息生成依赖。

#### C. 声明并实现Checker

```cpp
// health_core.h：新Checker声明
class VoltageChecker : public IHealthChecker {
 public:
  explicit VoltageChecker(const YAML::Node& quality);
  Findings check(const Sample& sample, Values& values) override;
 private:
  Bounds voltage_;
};
```

```cpp
// health_core.cpp：逻辑伪代码
VoltageChecker::VoltageChecker(const YAML::Node& q)
    : voltage_(configuredBounds(q["voltage_v"], true)) {}

Findings VoltageChecker::check(const Sample& s, Values& values) {
  values["voltage_v"] = s.voltage_available ? number(s.voltage_v) : "unavailable";
  if (!s.voltage_available) {
    // 这里假设电源数据是必需输入；可选数据应由配置决定是否报告缺失。
    return {Finding{"POWER_VOLTAGE_UNAVAILABLE", "voltage unavailable",
                    "POWER_VOLTAGE_UNAVAILABLE", "V", ERROR, 0, 0, true}};
  }
  if (!voltage_.enabled()) return {};
  const int level = voltage_.level(s.voltage_v);
  const double limit = level == ERROR ? voltage_.error
                     : voltage_.warning_enabled ? voltage_.warning
                                                : voltage_.error;
  return {Finding{"POWER_VOLTAGE", "voltage outside configured range",
                  "POWER_VOLTAGE", "V", level, s.voltage_v, limit, false}};
}
```

示例中的 `configuredBounds()` 是 `health_core.h` 已公开的配置解析函数，`true`表示低于阈值时告警。实际阈值由YAML覆盖。`Finding.id` 要稳定且唯一，因为 `RuleLatch` 用它追踪触发和恢复。此例假设电源输入必需；如果是可选输入，应增加 `require_available` 等明确规则，不要把所有缺失值都无条件报ERROR。

#### D. 注册Checker并校验配置

在 `CheckerFactory::create()` 增加分支：

```cpp
if (c.checker == "VoltageChecker")
  return std::unique_ptr<IHealthChecker>(new VoltageChecker(c.quality));
```

同时在 `qualityValidate()` 增加 `VoltageChecker` 分支：

```cpp
} else if (m.checker == "VoltageChecker") {
  keys(q, m.id + ".quality", {"voltage_v"});
  bounds(q["voltage_v"], true, {22.0, 20.0, true});
  if (m.adapter != "EnvironmentAdapter")
    throw std::invalid_argument("unsupported voltage adapter");
}
```

配置校验要明确接受哪些键、比较方向、单位、边界关系及允许适配器。否则未知或拼错字段容易被忽略，启动时就应报配置错误。

#### E. 在YAML启用模块和规则

```yaml
modules:
- id: power
  enabled: true
  checker: VoltageChecker
  adapter: EnvironmentAdapter
  topic: /robot/power
  required: true
  quality:
    voltage_v:
      enabled: true
      warning_below: 22.0
      error_below: 20.0
```

若使用bag配置，也要在 `health_bag.yaml` 加对应模块和Topic。YAML的阈值必须根据传感器量程、机器人供电规格和故障处置要求确定，示例数字不能直接用于实机。

### 2.4 新数据的流转和验证

```text
ROS消息
  -> InputAdapter检查字段并转换成SI单位
  -> Sample保存类型化值、源时间、接收时间和可用性
  -> ModuleMonitor.receive()
  -> StreamTracker检查时间戳；Checker检查单帧质量/历史变化
  -> Finding按稳定rule_id进入RuleLatch
  -> ModuleReport.values进入DiagnosticArray、RViz和metrics.0.csv
```

至少检查：

1. 有效值在正常范围，输出OK；
2. 刚越过WARNING阈值，报告WARNING；
3. 越过ERROR阈值或收到NaN/无效值，报告对应等级；
4. `enabled: false` 时业务阈值不触发；基础结构安全检查仍保留；
5. 值的单位转换只发生一次，日志显示的是声明的标准单位；
6. 重启或数据代际变化后，不用上一实例的历史值计算跳变。

## 3. 用话题控制受管进程 RUN/STOP

### 3.1 选消息语义

推荐用标准 `std_msgs/Bool`，不需要定义新 `.msg`：

| 消息 | 含义 |
| --- | --- |
| `data: true` | 请求目标进程组进入RUN |
| `data: false` | 请求目标进程组进入STOP |

这个话题是期望状态输入。控制器收到请求后调用已有 `start()` / `stop()`，再通过现有 `RuntimeState` 发布实际启动、停止结果。若控制话题发布者退出，最后一次状态仍保持；除非另外实现超时策略，否则控制器不会自动把它改回STOP。

### 3.2 修改 `runtime_controller_node.cpp`

文件：`src/runtime_controller_node.cpp`。需要在以下位置改：

1. **头部 include** 增加 `#include <std_msgs/Bool.h>`。
2. **Group 结构体** 增加 `run_stop_topic` 字段。
3. **YAML解析循环** 读取 `run_stop_topic`。
4. **进程组解析完成后** 创建订阅器；subscriber 对象放进类成员 vector，保证生命周期。
5. **增加请求处理函数**，把true/false送到已有 `start()` / `stop()`。
6. **start/stop 原因字段**增加来源信息，让事件日志能分辨服务请求和话题请求。
7. **类成员区** 增加 `std::vector<ros::Subscriber> run_stop_subs_`。

```cpp
// 文件头部
#include <std_msgs/Bool.h>
#include <vector>

// RuntimeController::Group
std::string run_stop_topic;

// RuntimeController类成员区
std::vector<ros::Subscriber> run_stop_subs_;

// 解析每个group时
g.run_stop_topic = n["run_stop_topic"]
                       ? n["run_stop_topic"].as<std::string>()
                       : "";

// groups_全部解析完成后，再创建Topic订阅
for (const auto& kv : groups_) {
  if (kv.second.run_stop_topic.empty()) continue;
  run_stop_subs_.push_back(nh_.subscribe<std_msgs::Bool>(
      kv.second.run_stop_topic, 10,
      [this, binding = kv.first](const std_msgs::Bool::ConstPtr& msg) {
        auto it = groups_.find(binding);
        if (it == groups_.end()) return;
        applyRunStopTopic(it->second, msg->data);
      }));
}

// RuntimeController私有方法；只处理状态变化，避免重复消息刷屏/反复发信号
void applyRunStopTopic(Group& g, bool run) {
  if (run) {
    // 已经要求RUN时，重复true不触发第二次start；进程崩溃后不会因重复true自动无限重启。
    if (g.desired == "RUN") return;
    // STOPPING期间不能并行启动同一驱动；等待STOPPED后重新发true。
    if (g.observed == "STOPPING") {
      const std::string reason =
          "RUN request received while STOPPING; send RUN again after STOPPED";
      if (g.reason != reason) {
        g.reason = reason;
        record(g, "RUN_REQUEST_DEFERRED");
      }
      return;
    }
    start(g, "run_stop_topic requested RUN");
  } else {
    // 已停止或正在停止时，重复false不重复发送SIGINT。
    if (g.desired == "STOP" &&
        (g.pid <= 0 || g.observed == "STOPPING")) return;
    stop(g, "run_stop_topic requested STOP");
  }
}

// 替换start/stop现有定义的函数签名和reason赋值；其余进程管理主体保留。
bool start(Group& g, const std::string& source = "explicit RUN") {
  // ...保留当前进程创建主体...
  g.reason = source;
  // ...继续fork/exec、record、publish...
}

void stop(Group& g, const std::string& source = "explicit STOP") {
  // ...保留当前进程停止主体...
  g.reason = source + "; waiting for child reap";
  // ...继续record、publish、向进程组发送SIGINT...
}
```

上面展示需要插入的位置和关键处理逻辑。实际落地时，省略号部分保留当前函数原有实现，并把原有“已停止”等原因文本与 `source` 合并。服务回调继续调用这两个函数，因此服务能力不会被移除。

### 3.3 运行配置增加雷达驱动组

建议新建 `config/runtime_lidar.yaml`，保留现有定位配置文件。以下示例只展示雷达组；若同一个控制器还要管理定位组，把原来的 localization 组也放在同一个 `groups` 列表里。

```yaml
state_topic: /robot_runtime/module_state
log_directory: ~/.ros/robot_health/runtime

groups:
- binding: lidar
  enabled: true
  run_stop_topic: /robot_runtime/lidar_enable
  # 用机器人上实际安装的驱动包和launch替换下方占位内容。
  command:
  - roslaunch
  - <actual_lidar_driver_package>
  - <actual_lidar_driver.launch>
  # 必须填写ROS Master中可查到的真实驱动节点全名。
  supervised_ros_node: /<actual_lidar_driver_node>
  autostart: false
  stop_timeout_sec: 5.0
  clean_exit_is_task_completion: false
```

`RuntimeController` 会启动自己创建的进程组，停止时发SIGINT并等待进程退出；它不是硬件电源开关，也不会接管已在另一个终端运行的驱动。`supervised_ros_node` 写错时，即使 `roslaunch` 进程还活着，控制器也可能报告节点不可用。

### 3.4 将健康监控的雷达模块绑定到 `lidar`

当前 `config/health_robot.yaml` 中 `id: lidar` 的模块配置是：

```yaml
lifecycle:
  control_binding: sensors
```

如果运行控制配置中的组叫 `binding: lidar`，需要把雷达模块改成：

```yaml
lifecycle:
  control_binding: lidar
```

`robot_health_monitor_node.cpp` 中的 `HealthRegistry::control()` 已按 `control_binding == RuntimeState.binding` 匹配状态，不需要为普通雷达组另写映射代码。IMU、测距等不由该驱动进程管理的模块继续使用各自正确的binding。

### 3.5 Launch与ROS服务

`launch/live_managed.launch` 已有 `runtime_config` 参数；通常不必改launch源码，启动时指定新配置：

```bash
roslaunch fastlio_health_monitor live_managed.launch \
  config:=/path/to/health_robot.yaml \
  runtime_config:=/path/to/runtime_lidar.yaml \
  rviz:=false
```

发送一次话题请求：

```bash
rostopic pub -1 /robot_runtime/lidar_enable std_msgs/Bool "data: true"
rostopic pub -1 /robot_runtime/lidar_enable std_msgs/Bool "data: false"
```

进程组也仍然可以通过既有服务控制。`ControlModule.srv` 和服务地址 `/robot_runtime/control` 不需要改：

```bash
rosservice call /robot_runtime/control "binding: 'lidar'\ncommand: 'RUN'"
rosservice call /robot_runtime/control "binding: 'lidar'\ncommand: 'STOP'"
```

服务返回 `accepted` 只表示请求被接受；最终结果要看 `/robot_runtime/module_state` 对应 `binding: lidar` 的 `observed_state`，例如 `RUNNING` 或 `STOPPED`。如果启停话题持续发布true，它会继续表达“期望运行”，可能抵消服务发出的STOP；实际系统应确定一个主要控制源，或加命令仲裁器。

使用 `std_msgs/Bool` 时，当前 `CMakeLists.txt` 和 `package.xml` 已有 `std_msgs` 依赖；不需要改 `RuntimeState.msg`、`ControlModule.srv` 或增加Livox依赖。需要运行真实驱动时，机器人上仍必须安装对应雷达驱动。

重复发布相同的 `true` 是幂等请求，不会对已经要求RUN的组重复调用start；这也避免进程崩溃后仅靠周期性true无限重启。若发生故障并希望人工再次启动，可以先发false，确认STOPPED，再发true。STOPPING时收到true会等待，需在STOPPED后重发。

## 4. 如果要根据健康诊断自动恢复，另外增加策略层

上面的Bool订阅仅响应外部控制程序的明确请求。它不会自动读取健康等级并作决定。

如果需求是“雷达诊断ERROR后自动重启驱动”，还要在运行控制器或独立C++策略节点中订阅健康输出 `/fastlio_health_monitor/diagnostics`，然后明确实现：

1. 只读取 `module_id=lidar` 对应的诊断项，检查 `DiagnosticStatus.level` 和具体错误规则；
2. 区分计划停止/启动期、真实数据故障和日志故障；
3. 设置持续时间门槛、重启冷却时间、最大重试次数和人工停止优先级；
4. 重新启动后等待真实驱动ROS节点和雷达数据恢复，不能只看启动命令返回；
5. 把触发原因、请求、结果和失败次数写进可追溯事件。

不能把任意ERROR直接映射为STOP：断流时STOP可能进一步阻断数据。也不要把健康状态再转换成同一个期望运行Bool并回发给自己的订阅端，否则容易形成控制反馈环。
