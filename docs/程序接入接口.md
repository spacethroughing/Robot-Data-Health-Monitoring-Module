# 程序接入接口

## 1. 最简单的接入方式

你的节点发布标准ROS话题，健康监控订阅。无需把监控代码塞进定位算法，也无需换FAST-LIO。换一个建图定位节点时，优先改YAML的topic、frame、频率和阈值。

```text
雷达节点 ──PointCloud2──┐
原始IMU ──Imu─────────┤
融合IMU ──Imu─────────┼→ C++健康监控 → DiagnosticArray / UInt8 / 日志
定位节点 ──Odometry────┤                       ↓
对地测距 ──Range（可选）┘                     RViz面板

你的真实管理程序 ──RuntimeState心跳──→ 正常关闭/重启状态识别
```

## 2. 默认输入接口

| 模块 | 话题 | 类型 | 程序读取什么 |
| --- | --- | --- | --- |
| lidar | /rslidar_points | sensor_msgs/PointCloud2 | header、width/height、XYZ字段、数据布局、点数与有效比例 |
| imu | /mavros/imu/data_raw | sensor_msgs/Imu | header、加速度、角速度、对应协方差与可用性 |
| imu_attitude | /mavros/imu/data | sensor_msgs/Imu | 上述IMU基础数据，加orientation四元数与姿态可用性 |
| localization | /Odometry | nav_msgs/Odometry | header/child_frame、位置、四元数、pose协方差；当前速度来源是位置差分 |
| ground_range | /mavros/rangefinder/rangefinder | sensor_msgs/Range | header、range、min/max_range、field_of_view；约3Hz |

### 生产者需要保证的内容

- header.stamp表示这条消息的实际源时间，不能每条都填0，也不要混秒/毫秒。不同数据时钟域标签不等于已校准绝对传输延迟。
- 同一数据实例时间向前；合法重启/参考系重置应通过运行控制协议通知，不要靠突然回退时间让监控猜测。
- PointCloud2必须有可读取的x/y/z字段，布局与缓冲区匹配；不要求特定雷达驱动品牌。
- MAVROS配置按m/s²、rad/s；orientation_covariance[0]=-1代表未提供姿态。原始IMU没姿态不代表融合IMU也没有。
- Odometry的header.frame_id和child_frame_id要与配置匹配；更换map/odom/base_link体系要同步修改。协方差不是定位真值误差。
- Range单位米；NaN无效，±Inf表示无可用定量距离的状态，不能填成0高度。当前适配连续测距，不支持把二值定距开关当成连续高度计。
- 默认标准构建不含Livox消息依赖；已有livox_ros_driver时可用--livox启用CustomMsg适配器，也可由驱动直接发布标准PointCloud2。

## 3. 输出接口

| 话题 | 类型 | 含义 |
| --- | --- | --- |
| /fastlio_health_monitor/diagnostics | diagnostic_msgs/DiagnosticArray | 总体、各模块、日志健康；包含运行状态和键值指标，建议业务系统订阅此接口 |
| /fastlio_health_monitor/status | std_msgs/UInt8 | 简单0/1/2，分别OK/WARNING/ERROR；启动、暂停、停止等详细原因仍应读diagnostics |

诊断键值包括：module_id、operating_state、operational_valid、data_health_level、age_sec、rate_hz、module_epoch、roll_deg、pitch_deg、range_raw_m、range_status等。

NO_DATA是可选输入尚未接入，模块本身不是有效数据，也不被伪造为OK；初始不参与总体。收到首帧后contributes_to_overall=true，质量异常/后续断流开始影响总体。业务程序应读取operational_valid和operating_state，不要只看一个绿色或一个数字就认定所有输入都有。

RViz只是诊断消费者。机器人端没有GUI也会发布同样的诊断与日志。

## 4. 正常启停接口：RuntimeState

默认输入话题 `/robot_runtime/module_state`，类型 `fastlio_health_monitor/RuntimeState`。消息定义在包内msg/RuntimeState.msg。

| 字段 | 填写要求 |
| --- | --- |
| header.stamp | 当前ROS时间，用于追溯；监控心跳年龄用接收单调时间判断 |
| binding | sensors或localization，与模块lifecycle.control_binding匹配 |
| controller_id | 控制器稳定标识，本次控制器内不要乱变 |
| controller_run_id | 本次控制器运行ID，便于日志关联 |
| producer_instance_id | 被管理数据生产实例ID；真正重启时换新ID，普通心跳不要每次换 |
| command_id | 同一次RUN/STOP命令的ID；新命令生成新ID |
| sequence | 从大于0的数起，每条消息递增，不能重复/倒退 |
| frame_epoch | 合法数据参考/时间基准重置时递增，普通数据不变 |
| desired_state | RUN / STOP / PAUSE |
| observed_state | STARTING / RUNNING / STOPPING / STOPPED / PAUSED / FAULT |
| reason | 真实原因，说明实际动作或状态 |
| exit_code | 管理进程退出结果；不能只因0就推断正常任务结束 |
| trace_healthy | 控制器自己的追溯记录是否正常；按真实日志结果填写 |
| controller_log_directory | 控制器日志路径 |
| data_reference | 可选bag引用路径；实机未知时留空 |
| data_sha256 | 仅兼容旧消息结构，新版发送空；不计算、不写入日志 |

发布要求：**非latched、持续心跳**，建议与内置控制器一样约5Hz。当前1秒心跳WARNING、3秒ERROR；只发一次STOPPED不能无限维持正常停机状态。旧实例/乱序消息会被拒绝。

状态流程：

```text
要求开始 → RUN/STARTING → 生产者确实启动 → RUN/RUNNING
要求正常停 → STOP/STOPPING → 确认已停止 → STOP/STOPPED（继续心跳）
要求重启 → 新producer_instance_id → RUN/STARTING → RUN/RUNNING
实际故障 → RUN/FAULT
```

监控收到RUN后仍要看实际数据和连续就绪条件，不会仅凭RUNNING字符串就认定定位有效。正常PAUSED/STOPPED暂停数据需求超时；坏消息实际到达仍可记录质量问题。没有可信状态时，消息消失只能当成未知原因的断流。

### 不建议用临时rostopic pub伪造正常状态

业务接入应来自真正负责进程生命周期的管理者。包内robot_runtime_controller_node可实际拥有定位进程并发布状态；已有机器人管理器也可以在自己的实际启停回调中发上述消息。

## 5. 内置托管控制服务

服务 `/robot_runtime/control`，类型 `fastlio_health_monitor/ControlModule`：

```text
请求：binding、command
响应：accepted、command_id、producer_instance_id、reason
```

默认示例只托管localization，常用RUN/STOP，合法参考系重置用RESET_FRAME。PAUSE/RESUME只适用于配置了回放状态源的受管理回放组，不是任意实机定位程序的通用暂停接口。

务必先配置scripts/start_localization.sh和runtime_localization.example.yaml中的实际ROS节点名。autostart=false时需要服务RUN；STOP后等STOPPED确认再重启。服务accepted表示接受要求，最终是否成功仍看状态心跳与数据。

## 6. 回放接口

replay.launch拥有 `/recorded_bag_playback`，它启动原生rosbag播放器并发布非latched控制状态。

- `/recorded_bag_playback/pause`：std_srvs/SetBool，true暂停、false恢复。
- `/recorded_bag_playback/state`：RuntimeState，回放源状态。
- `/robot_runtime/module_state`：RuntimeState，通知sensors/localization绑定的数据需求变化。

健康节点确认发布者、bag引用、退出/EOF原因和已参与模块STOPPED后才封存日志；进程退出码0不能单独证明正常完播。封存后重播需新run。

## 7. 接入感知/规划等其他模块

已有实现可复用：

- DiagnosticRelayAdapter + RelayChecker：订阅DiagnosticArray，保留生产者语义质量；空数组不能当作全部正常。
- PathAndTaskStateAdapter + PlanningChecker：nav_msgs/Path和TaskState任务心跳，有目标才检查结果期限，无目标可IDLE。
- PoseStampedAdapter + LocalizationChecker：不提供twist/协方差时要按实际能力配置，不能假装存在。

不同类型都需要单独的modules配置。核心扩展接口为IInputAdapter、IHealthChecker和两个工厂；新功能类用C++实现。本部署默认五模块不会自动订阅你尚未配置的感知/规划节点。

## 8. 精简日志与控制协议的区别

本版JSONL、CSV、manifest不再输出指定的五个字段，CSV还去掉旧epoch列。内部控制消息仍保留生产实例和frame_epoch，保证正常重启、旧心跳拒绝与坐标系重置功能不受影响。RViz诊断可继续展示内部数据代际；这不代表日志仍写该字段。
